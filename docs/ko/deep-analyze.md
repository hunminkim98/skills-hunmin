# deep-analyze

[English](../en/deep-analyze.md) · [문서 홈](README.md) · [SKILL.md](../../cursor/deep-analyze/SKILL.md)

당신이 물은 것만 조사합니다. 프로젝트는 바꾸지 않습니다. 도움이 되어 보이려고 범위를 넓히지 않습니다.

## 왜 만들었나요

공개된 "이 레포를 연구해" 스킬은 `research/` 폴더, HTML 브리핑, SaaS 제안서를 자주 만듭니다. "딥 리서치" 스킬은 질문보다 넓은 답을 내거나, 유료 API를 요구하는 경우가 많습니다.

이 스킬은 반대로 썼습니다. **엄격하고, 읽기 전용이고, 범위가 고정**입니다. 확신에 찬 틀린 답이 느린 맞는 답보다 비쌉니다. 감을 확인하지 말고, 답을 깨는 쪽을 찾습니다.

감사와 "이게 정말 맞아?"에 씁니다. 고치는 구현에는 쓰지 않습니다.

## 원리

규칙 순서입니다.

1. **읽기 전용.** 생성, 수정, 삭제, 이동, 커밋, 설치, 푸시, 배포, 위키 쓰기 없음. 읽기·검색·가져오기는 됩니다. 출력만 하는 명령(`git log`, `git show`, 트리를 바꾸지 않는 기존 테스트)은 질문에 그 증거가 필요할 때 허용합니다.
2. **범위 고정.** 대상이 없으면 확인을 **한 번만** 하고 멈춥니다. 더 넓은 조사를 지어내지 않습니다.
3. **주장보다 근거.** 무게 있는 사실은 경로와 줄 범위, URL, 또는 명령과 결과가 있어야 합니다. 학습 기억은 근거가 아닙니다. 출처를 못 보여 주면 `unverified` 또는 `insufficient evidence`를 쓰고, 그 정확한 숫자·인용·날짜는 버립니다.
4. **답을 공격.** 끝내기 전에, 본 답을 틀리게 만들 가설을 하나 검사하고 무엇을 봤는지 적습니다.
5. **개선 제안 없음.** 지금 참인 것만 말합니다. 같은 요청에서 묻지 않는 한 리팩터나 "다음에 이렇게"는 없습니다.
6. **질문과 같은 언어.**

단계는 나눕니다. **범위 → 수집 → 검증 → 종합.** 수집이 열린 동안 보고서를 쓰기 시작하지 않습니다.

수집은 당신의 말과 동의어를 같이 씁니다. 코드 질문은 문서만이 아니라 구현을 읽습니다. 웹 질문은 공식 문서, 소스, 표준을 우선합니다. 열지 않은 제목은 인용이 아닙니다. 바깥세상 주장은 독립 출처 두 개, 아니면 `[single-source]`. 코드 사실은 읽은 정본 구현 하나로 충분합니다.

채팅 보고서는 [`references/report-shape.md`](../../cursor/deep-analyze/references/report-shape.md)를 따릅니다. 답, 근거, 무엇이 이것을 틀리게 하는지, 공백, 실제로 연 출처.

검색을 더 해도 답이 안 바뀌거나, 남은 공백이 분명하면 멈춥니다. 양이 엄밀함이 아닙니다. 유료 리서치 API는 필요 없습니다. 하위 에이전트는 범위 안의 독립된 두 각도일 때만 씁니다.

무기, CSAM, 멀웨어, 신상 털기처럼 해로운 이중 용도 요청은 짧은 거절 한 문단입니다. 절차는 없습니다.

## 언제 쓰나요

주장, 경로, 계약, 페이지가 맞는지 알고 싶고 파일은 건드리고 싶지 않을 때 `/deep-analyze`를 씁니다.

"구현해 줘", 프롬프트 다시 쓰기, 위키 closeout, 여러 이해관계자의 트레이드오프([discussion](discussion.md))에는 쓰지 마세요.

이 스킬은 **슬래시로만** 켭니다.

## 설치

```bash
npx skills add hunminkim98/skills-hunmin --skill deep-analyze --agent cursor
```

프로젝트/전역은 [문서 홈](README.md)을 보세요.

## 사용 방법

1. 새 Agent 채팅.
2. `/deep-analyze`와 구체적인 질문 ("finalize 락은 배치 행이야, 오브젝트 키야?").
3. 대상이 흐리면 확인 질문 하나에 답합니다.
4. 답 → 근거 → 무엇이 이것을 틀리게 하는지 → 공백 순으로 읽습니다.

깨끗한 실행 뒤에는 `git status`에 새 파일이 없어야 합니다.
